# Browsless MCP companion

Build normal Browsless workflow drafts from Claude Desktop, Codex, or another
MCP-compatible application. No provider API keys or hosted backend are needed.

The companion exposes MCP over **stdio** and a separate authenticated HTTP bridge
bound only to `127.0.0.1`. It is not a public HTTP MCP server.

## Run from a checkout

Requires Node.js 22+ for running the companion and Bun for repository development.
From the Browsless repository root:

```sh
bun install
bun run build:mcp
```

Configure your MCP client with an **absolute path**:

```json
{
  "mcpServers": {
    "browsless": {
      "command": "node",
      "args": ["/absolute/path/to/browsless/packages/mcp/dist/index.js"]
    }
  }
}
```

For Codex, the equivalent configuration is:

```toml
[mcp_servers.browsless]
command = "node"
args = ["/absolute/path/to/browsless/packages/mcp/dist/index.js"]
```

The client starts the process. Do not run a second instance on the same port.
If the client's startup environment cannot find Node, use its absolute path.

### OpenCode in this repository

The repository's `opencode.json` configures `mcp.servers.browsless` to run the local
build automatically. Run `bun run build:mcp` first, then check `opencode mcp list`
or `/mcps`. OpenCode watches configuration changes; `/reload` can force a reload.
An MCP connection does not mean the extension is paired: call
`get_connection_info` and approve in Browsless as described below.

This companion uses the classic MCP handshake, so the configuration explicitly
selects `protocol: "legacy"`. Stop other clients using the same companion port
before testing through OpenCode.

## Pair

1. Load the matching Browsless extension build and open its dashboard.
2. Ask the AI to call `get_connection_info` and display the port and pairing code.
3. Open **Settings → External AI** in Browsless.
4. Enter the port and code, read the permission scope, and approve.
5. Ask the AI to discover blocks, validate a workflow, and create a draft.

Keep the paired dashboard window open. Switching dashboard routes is fine.
Only one dashboard can pair to a companion instance. Disconnect to switch windows or
profiles. Approval is kept in memory, not persisted. Restarting either side requires
pairing again. Codes expire after ten minutes; sessions expire after thirty seconds
without communication. A suspended dashboard may therefore need pairing again.

The AI can discover block definitions, validate graphs, and create **new disabled
drafts**. It cannot run them, enable triggers, inspect pages, read existing
workflows/credentials, or overwrite workflows. Review each block and explicitly
enable the draft in Browsless before running it.

## Tools

- `get_connection_info`
- `list_blocks`
- `get_block_schema`
- `validate_workflow`
- `create_workflow_draft`

Block metadata comes from the **connected extension**, not a stale embedded
catalog. Validation checks structure, graph connections, and default-derived
field types. It does not prove complete block-specific semantics or runtime
correctness. Notes, block packages, and embedded block groups are not authorable
through this initial API; use normal connected nodes instead.

Example `workflow` argument:

```json
{
  "name": "Read a page heading",
  "nodes": [
    { "id": "start", "block": "trigger", "data": { "type": "manual" } },
    {
      "id": "open",
      "block": "new-tab",
      "data": { "url": "https://example.com", "waitTabLoaded": true }
    },
    {
      "id": "read",
      "block": "get-text",
      "data": {
        "selector": "h1",
        "saveData": false,
        "assignVariable": true,
        "variableName": "heading"
      }
    }
  ],
  "edges": [
    { "source": "start", "target": "open" },
    { "source": "open", "target": "read" }
  ]
}
```

There must be exactly one manual trigger. Every node must be reachable from it.
Omitted edge `output`/`input` values default to `"1"`. Conditional outputs use IDs
from the condition configuration, or `"fallback"`. Query `get_block_schema`
before configuring a block. Layout, native handles, defaults, and persistence
settings are generated by the extension.

## GitHub distribution

No npm publication is required. The repository includes
`.github/workflows/release-mcp.yml` to build, check, package, and publish GitHub
Release assets automatically.

1. Set the intended version in `packages/mcp/package.json` and run `bun install`
   to update the workspace version in `bun.lock`.
2. Commit the intended source changes, including the workflow and lockfile.
3. Push a tag that exactly matches that version:

   ```sh
   git tag mcp-v0.1.0
   git push origin mcp-v0.1.0
   ```

The tag's commit must contain the workflow. GitHub Actions must be enabled.
The workflow validates versions, runs both typechecks and lint, builds both
surfaces, checks MCP integration, and tests `npx` installation from the packed
archive before publishing `browsless-mcp-0.1.0.tgz` and its SHA-256 checksum.
Publishing uses GitHub's built-in `GITHUB_TOKEN`; no npm token or personal access
token is required. Organization policy must permit the publish job's
`contents: write` permission.

Versions such as `0.2.0-rc.1` become GitHub prereleases. MCP releases do not replace
the repository's "latest release" designation, which may belong to the extension.
Existing releases/assets are never overwritten: bump the version for a new
release. A manual **Run workflow** validates and uploads temporary Actions
artifacts only; it does not publish a GitHub Release.

To package manually instead, build and run `bun pm pack` from this directory.
Users can configure `npx` with the actual release URL:

```json
{
  "mcpServers": {
    "browsless": {
      "command": "npx",
      "args": [
        "--yes",
        "--package=https://github.com/OWNER/REPOSITORY/releases/download/TAG/browsless-mcp-0.1.0.tgz",
        "browsless-mcp"
      ]
    }
  }
}
```

Replace OWNER, REPOSITORY, and TAG with an existing release.
The repository is a monorepo: pointing `npx`
at its root is **not** equivalent to installing this standalone package. Pin a
reviewed release; do not install untrusted companion packages.

## Configuration and troubleshooting

- `BROWSLESS_MCP_PORT` overrides port `38491` (1024–65535). Set it in your client's
  MCP server environment and enter that same port in Browsless.
- The current dashboard is a single-instance popup window. Connect one AI client at
  a time per browser profile. Separate profiles can use separate companion ports.
- Connection refused: ensure the AI client started the companion, and check its
  stderr logs. All diagnostics use stderr; stdout is reserved for MCP messages.
- Address already in use: stop the earlier instance or choose another port.
- Pairing rejected: obtain current connection info; check the port, code, and
  whether another dashboard is paired. After repeated failures wait one minute.
- After a creation timeout, inspect the dashboard before retrying: a draft might
  already have been saved. Requests are not automatically replayed.
- Local browser security/network policy may block loopback requests. The bridge
  intentionally accepts only Chrome-extension origins, not ordinary web pages.

Manual approval is not a code sandbox. Drafts can contain JavaScript, webhooks,
templates, and destructive automation. Do not enable untrusted drafts. The
companion has the same OS-level trust as any local program you install.
