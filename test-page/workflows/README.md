# Playground workflows

The saved Profile, Inputs, Catalog, Dialog, Waiting, and Iframe workflow JSON files contain multi-step embedded package blocks. **Run all playground workflows** exercises these packages and checks their output connections. Shadow DOM and CSV remain direct-block tests. There is no workflow generator.

## Automatic development loading

With `bun run dev`, opening the dashboard or popup seeds missing test workflows alongside the normal defaults. `src/utils/developmentFixtures.ts` reads the saved `all-playground.browsless.json` and `all-packages.browsless.json` bundles directly; it does not construct or rewrite their graphs. These files are excluded from production builds. Existing saved workflows, local edits, and intentional deletions are preserved, not automatically upgraded.

Edit the two bundle JSON files to change the automatically seeded fixtures. Individual JSON files are standalone manual-import copies; if you change one, update the corresponding `includedWorkflows` entry in its bundle as well. Package blocks are stored directly in each workflow's `drawflow.nodes[].data`, not generated by runtime code.

The JSON files below remain available for optional manual imports, backups, and restoring deleted fixtures. Avoid importing duplicates if the automatic development list is already present.

There is also a separate six-package integration suite: **Playground · Run all package tests** (`all-packages.browsless.json`), with six individual `package-*.browsless.json` wrappers. See [the package guide](../packages/README.md) for internal step counts, Library imports, output checks, and snapshot behavior.

Each workflow scrolls once to its test section and uses a 650 ms block delay to make the run visible, without repeated per-element scrolling. To use updated fixtures in existing development storage, import the individual JSON files as new copies, or deliberately delete the old test fixtures and clear `developmentWorkflowIds` from extension local storage before reopening the dashboard. The loader does not overwrite existing workflows.

## Import and run

1. Start the development extension with `bun run dev`.
2. Enable **Allow access to file URLs** for **BrowsLess-Dev** in Chrome's extension details.
3. In the BrowsLess dashboard, use **Import workflow** and select **`all-playground.browsless.json`**. This uses the extension's existing `includedWorkflows` format to import the suite and eight child workflows.
4. Run **Playground · Run all playground workflows**, or run any child individually. Each child opens a fresh local page; leave it open and run workflows one at a time. The suite leaves eight tabs open and downloads one sample CSV.
5. Inspect the suite's execution-log variables: **`allPassed`** and **`results`**. Individual workflows expose **`result.passed`** and **`result.checks`**, plus extracted values listed below. A green execution status alone means the blocks finished, not that every check passed. Checks report booleans without interrupting the suite; block errors stop execution.

You can instead import any individual `.browsless.json` file. Do not import the suite and individual copies together unless you want duplicates. Reimporting the suite skips included children with existing IDs; to update them, delete the old playground suite/children before importing again, or import the changed individual file as a new copy.

## Local paths

Manual imports use the checked-in `playgroundUrl` in **Global data** (`file:///Users/pawel/browsless/test-page/test-page.html`). Change it if your repository is elsewhere. Development auto-seeding adapts only this URL to the current repository location; the saved workflow graphs remain unchanged. The suite passes its Global data to every child, so changing the suite's URL is sufficient when running the whole pack.

These fixtures intentionally use **New tab**, not **Active tab**: Active tab currently rejects non-HTTP URLs. There are no scheduled, startup, or visit-web triggers, external requests, or permission changes.

## Manual-only checks

- Native alert/confirm: use the page's buttons and respond manually. They are not part of the unattended suite.
- File upload: use the page's file picker with a local dummy file. No machine-specific upload path is embedded.
- Download: check Chrome's download list and the CSV on disk. The workflow verifies the link's metadata/content, not download completion.
- Form validation: submit the blank form, then try an invalid email or short password; Chrome should prevent submission. The profile workflow covers the valid path.

These are development fixtures, not an automated browser test suite. JSON structure and embedded script syntax can be checked locally; full extension behavior must still be verified in Chrome with file access enabled.
